# ADR-SOC-27: 依赖管理由编译器静态承担（不变式 D-1/D-1′/D-2/D-3 + 架构保证 A-1/A-2）

> **状态**: 📋 Proposed（**待签批**）
> **日期**: 2026-10-29
> **Owner**: ArchForge Team
> **影响**: 自研 ISA 的依赖层规范；SM 的 `HazardTracker` / `WritebackUnit` 形态；编译器 pass 集
> **类别**: ISA 依赖管理 / 正确性责任分配
> **实施**: OpenSpec change（待建）—— B-0..B-3

## 1. 背景

依赖管理要回答两个问题：**正确性由谁保证**、**什么时候保证**。现有三种做法互斥：

| 做法 | 机制 | 正确性保证者 | 代价 |
|---|---|---|---|
| **NVIDIA 式** | stall counter + 6×SB + DEPBAR + yield | **编译器**（提示错 ⇒ 程序结果错） | 41 bit/warp（0.09% RF） |
| **AMD 式** | TLB scoreboard + 类型化计数器 + `s_waitcnt` | **硬件** | 未公开；wait 指令占 issue 槽 |
| **学术全 scoreboard** | 每寄存器两块 scoreboard | **硬件** | **5.32% RF**，且实测**更慢**（0.97×） |

三者**不可直接拼接**（隐含前提互斥），且都留下一个未解决的问题：**谁为"提示写错"负责**。

自研 ISA 有一个三者都没有的资产：**操作数供给层（OSF/MCOS）可按 tag 校验**（33 号 §4.1.2 证明「槽值恒等于 RF 当前值」）。这让"值身份"的正确性可以**交回硬件**，只把"时序"留给编译器。

## 2. 决策

### D1 —— 不设硬件 scoreboard

**ISA 不提供逐寄存器的依赖 scoreboard。** 依赖状态规模 **∝ 在飞可变延迟生产者数**（而非寄存器数），由 **per-warp 8 个 SB 槽**承载。

### D2 —— 三条不变式（**必须逐指令类机械可检查**）

| 不变式 | 内容 | 检查方式 |
|---|---|---|
| **D-1** | 对每个**非豁免**指令类 `c`：`D_c ≤ L_w,min`（源锁存窗口 ≤ 写可见延迟） | 与 E-14 延迟表逐类核对 |
| **D-1′** | 对每个**豁免**指令类 `c`：`D_c − L_w,min ≤ 15`（= `stall` 字段上界）。**规范条款在本行**（与 40 号 §4.1 的 D-1′ 一致）；**推导**（gap-stall 可表达性）见 [`ADR-SOC-28`](./ADR-SOC-28-late-addr-war-via-gap-stall.md) §2 D2，本 ADR **不重复** | 与 E-14 延迟表逐类核对（豁免类） |
| **D-2** | 每 warp 可区分的在飞可变延迟生产者 **≤ 8**（**架构契约**，冻结后不得靠加深硬件队列突破） | 编译器槽分配不产生 > 8 个在飞生产者 |
| **D-3** | 复用 / 宽度提示**不得影响可观察语义** | 提示字段全 0 与任意取值的差分测试结果一致 |

### D3 —— 两条架构保证（**把"值身份"交回硬件**）

| 保证 | 内容 |
|---|---|
| **A-1 值身份** | 经操作数槽交付给消费者的值，与其被读取时寄存器堆中对应 `(warp, reg)` 的值**逐位相同**（⚠ 与编译器算法族 `M-1..M-4`（39 号 §6）是**两套编号**，勿混） |
| **A-2 槽生命周期** | 槽中值在寄存器被改写时**立即失效**；失效不改变任何指令的可观察语义 |

⇒ **推论**：编译器对**复用提示 / 宽度提示**的任何错误，**只影响性能，绝不产生错误值**。这是新 ISA 相对 NV / AMD 的核心增量。

### D4 —— `L_w,c` 是**精确的架构承诺值**（不是上界也不是下界）

| 类别 | 约束 |
|---|---|
| 固定延迟类（由 `stall` 保护） | 目的寄存器**恰在** `issue + L_w,c` 可见。**不得更早**（击穿 WAR 紧边界）、**不得更晚**（`stall` 保护的 RAW 读到陈旧值） |
| 可变延迟类（由 SB 槽保护） | 可见时刻**不得早于** `issue + L_w,c`；更晚无妨 |
| 全局 | 任何类 `L_w,c ≥ L_w,min = 4` |

### D5 —— 依赖控制块（**按域裁剪，唯一口径**）

| 域 | 位宽 | 字段 |
|---|:---:|---|
| **向量** | **21** | `stall 4` + `sb_id 3` + `wait_mask 8` + `reuse_flags 3` + `budget_hint 2` + `yield 1` |
| **标量** | **16** | `stall 4` + `sb_id 3` + `wait_mask 8` + `yield 1` |

裁剪依据：① `reuse_flags`/`budget_hint` 只作用于 VGPR（MCOS 槽键为 `(bank, op_pos)`）；② `width_hint` 由 opcode 变体承载；③ **WAR 不占任何字段**（见 ADR-SOC-28）。

### D6 —— 槽耗尽的退路（**E-7b，不可缺失**）

编译器在超过 8 个在飞可变延迟生产者时**必须**二选一：① 合并到同一槽（同 `wait_mask` 位 ⇒ 并集等待）；② 插 `dep.wait` 排空。**两种退路都不得死锁**（生产者必然完成 ⇒ 计数必然归零）。

## 3. 选项对比

| # | 选项 | 结论 | 理由 |
|---|------|:----:|------|
| **1** | **纯 NV 式**（stall counter + 6 SB + DEPBAR + WAR 槽） | ❌ 否决 | 正确性**全押编译器**（提示错 ⇒ 结果错），无 A-1/A-2 兜底；且 **WAR 槽**在 ADR-SOC-28 已证明可用 `stall` 表达 ⇒ 12 bit/warp 是纯浪费 |
| **2** | **纯 AMD 式**（TLB scoreboard + `s_waitcnt`） | ❌ 否决 | 编译器零负担，但 **wait 指令占 issue 槽**、指令数增加；且与本仓"编译器驱动依赖层"的主线相反（要放弃 ISA 层的确定性） |
| **3** | **学术全 scoreboard** | ❌ 否决 | **5.32% RF**，是 NVIDIA 式 59×、本方案 **44×**；且实测**更慢**（0.97×）、精度略差 |
| **4** | **NV + D-1 不变式（无 tag 兜底）** | ❌ 否决 | 面积最小，但复用提示写错仍会**产生错误值** ⇒ 违背 D-3 |
| **5** | **本方案（不变式 + tag 兜底 + 控制块按域裁剪）** | ✅ **采纳** | 面积 **0.121% RF**（53 bit/warp），是学术方案的 1/44；正确性责任**清晰二分**：值身份→硬件（A-1/A-2）、时序→编译器（不变式可机械检查） |

## 4. 后果

### 4.1 正面

- **面积可控且可核算**：53 bit/warp × 48 warp = 2544 bit/SM = **0.121% RF**；
- **正确性责任清晰**：A-1/A-2 使**值身份**由硬件保证 ⇒ 编译器提示错降级为性能问题；
- **不变式可机械检查**：D-1 / D-1′ / D-2 都能对着 E-14 延迟表逐类核对 ⇒ **不依赖实测**即可判定；
- **控制块按域裁剪**：标量域省 5 bit，让 48-bit 标量形态恰好装满（`11 + 21 + 16 = 48`）。

### 4.2 负面

- **编译器负担显著**：需实现 **M-1**（延迟填充，含 RAW/WAR 两类 `stall` 义务的分配与 max 合成）、**M-2**（槽分配，**唯一有真正难度者**：依赖图着色 + 域政策 + 槽耗尽处理）、**M-3**（复用提示）、**M-4**（late-addr 判定，含 W-1/W-2 实例级验证）；
- **`D-1` 是紧边界**：`D_mem = 4` 与 `L_w,min = 4` 取等 ⇒ 任何把 `L_w` 下调到 3 的"优化"都会击穿标准访存的 D-1 ⇒ **D4 的精确承诺不可协商**；
- **D-2 是架构契约**：冻结后**不得**靠加深硬件队列提升 MLP ⇒ 微架构的自由度被换走；
- **依赖延迟必须自测**：AMD 不公开 SALU 吞吐与 SMEM 延迟 ⇒ 标量域参数须自研微基准。

### 4.3 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **编译器做不出 M-2** ⇒ 正确性论证不闭合 | 高 | B-3 是硬门禁；未过不得推进 B-4/B-5 |
| `L_w` 实现得比声明值晚 ⇒ RAW 读到陈旧值 | 高 | D4 写成架构承诺；verifier 用差分测试对拍"声明值 vs 实际可见时刻" |
| 槽耗尽路径在真实 kernel 上频繁触发 ⇒ 性能塌陷 | 中 | E-7b 的两条退路都实现；监控 `dep.wait` 插入频次 |
| 标量域实测 `L_w = 3` ⇒ 实现需插延迟对齐 | 低 | 实现侧插延迟（架构可见时刻仍为 4），或同步收紧该类 `D_c` |

## 5. 实施

| 阶段 | 内容 | 门禁 |
|---|---|---|
| **B-0** | 规范落地：40 号 §4（不变式 / 保证 / 控制块 / 延迟表 schema / 槽语义） | 本 ADR 签批 |
| **B-2** | 汇编器 + **M-1**（延迟填充）+ **M-4** | 单指令级差分 100% 通过 |

- [ ] **V1**〔本仓〕：**40 号附录 B 的机械化检查清单 14 项全部可执行且通过** — 验证手段：把检查清单写成脚本并对 E-14 延迟表跑通；责任人：verifier
- [ ] **V2**〔CppTLM〕：**A-1 成立**（槽交付值 ≡ RF 当前值） — 验证手段：随机填值 + 随机提示组合的差分测试（提示全 0 vs 任意取值）终态一致；责任人：verifier
- [ ] **V3**〔CppTLM〕：**A-2 成立**（寄存器改写使槽立即失效） — 验证手段：写后立即复用槽的专项用例；责任人：verifier
- [ ] **V4**〔CppTLM〕：**D-1 / D-1′ 逐类核对通过**（D-1′ 的推导来源见 ADR-SOC-28） — 验证手段：E-14 延迟表逐行核对记录归档；**前置**：标量域 `D_c` 真值须先关闭（40 号 T-1），否则标量类无法核对；责任人：verifier
- [ ] **V5**〔CppTLM〕：**`L_w` 的"精确承诺"在实现中成立** — 验证手段：实测「目的寄存器可见时刻 − issue」恒等于声明值（容差 0）；责任人：verifier
- [ ] **V6**〔CppTLM〕：**槽耗尽不 deadlock** — 验证手段：构造 > 8 个在飞可变延迟生产者的用例，观察合并/排空两条退路均收敛；责任人：verifier
- [ ] **V7**〔本仓〕：**依赖面积核算成立** — 验证手段：按 53 bit/warp × 48 warp 复算 = 0.121% RF，与综合估算偏差在可接受范围；责任人：build
- [ ] **V8**〔本仓〕：**边界声明落地**（33/35 号的 WAR 计数器条款带后端限定） — 验证手段：`grep -n "仅 NV 建模后端" docs/architecture/33*.md docs/architecture/35*.md` 命中 4+ 处；责任人：文档 owner
