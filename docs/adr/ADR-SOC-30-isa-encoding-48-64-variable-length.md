# ADR-SOC-30: ISA 指令编码 —— 48/64 bit 变长 + 11-bit opcode + 控制块按域裁剪

> **状态**: 📋 Proposed（**待签批**）
> **日期**: 2026-10-29
> **Owner**: ArchForge Team
> **影响**: 自研 ISA 的指令编码格式、解码器、编译器后端的目标码生成
> **类别**: ISA 编码 / 二进制格式
> **实施**: OpenSpec change（待建）—— B-0 / B-2 / B-5
> **关联**: [`40-new-isa-spec-skeleton.md`](../architecture/40-new-isa-spec-skeleton.md) §3（本 ADR 的规范条款）· [`36-new-isa-dependence-layer-design.md`](../architecture/36-new-isa-dependence-layer-design.md) §4.5（编码推演）· [`ADR-SOC-27`](./ADR-SOC-27-compiler-driven-dependence-management.md)（控制块宽度的来源）· [`ADR-SOC-29`](./ADR-SOC-29-dual-domain-scalar-vector-structure.md)（寄存器字段宽度）
> **取代**: 36 号 **Q-3** 的旧论证（4-bit opcode + 6-bit 寄存器索引 ⇒ "48 bit 恰好装下典型 3 源 ALU"）—— **结论保留，论证作废**

---

## 1. 背景

ISA 的编码格式一旦冻结就是**最硬的契约**：它同时决定取指带宽、解码器复杂度、编译器后端的码生成，以及**未来的演进空间**。

关键输入：

| 输入 | 值 | 来源 |
|---|---|---|
| 依赖控制块（向量 / 标量） | **21 / 16 bit** | ADR-SOC-27 |
| SGPR / VGPR 索引 | **7 / 8 bit** | ADR-SOC-29 |
| 指令形态 | 标量 1–2 源、向量 1–3 源 | ADR-SOC-29 |

⚠ **一条已被推翻的旧论证**：36 号 v1.2 用「4-bit opcode + 6-bit 寄存器索引」推出"48 bit 恰好装下典型 3 源 ALU"。但寄存器字段实际是 7/8 bit ⇒ **该推演的字段宽度是错的** ⇒ 必须按真实字段重算，且**结论可能翻转**。

## 2. 决策

### D1 —— 双长度变长编码：**48 / 64 bit，16-bit 粒度**

指令长度为 **48 bit（3 音节）或 64 bit（4 音节）**，**起点 2 字节对齐**。

### D2 —— 格式类（`fmt`）与长度判定

`fmt` 位于**指令 bit[2:0]**，**3 bit、8 类**，长度由 `fmt` **唯一决定** ⇒ **解码只需 2 字节前瞻**。

| `fmt` | 类 | 域 | 源数 | 长度 |
|:---:|---|:---:|:---:|:---:|
| `000` | `SOP1` | 标量 | 1 | 48 |
| `001` | `SOP2` | 标量 | 2 | **48 精准** |
| `010` | `SOPC` | 标量 | 2 | 48 |
| `011` | `SOPK` | 标量 | 1 | 64 |
| `100` | `SOPP` | 标量 | 0 | 48 |
| `101` | `VOP1` | 向量 | 1 | **48 精准** |
| `110` | `VOP2`（含 `LSU`） | 向量 | 2 | 64 |
| `111` | `VOP3` | 向量 | 3 | **64 精准** |

### D3 —— 位宽核算（**8 种形态均不溢出；3 种恰好填满**）

| 形态 | opcode | 寄存器/立即数 | 控制块 | 合计 | 长度 |
|---|:---:|---:|:---:|:---:|:---:|
| `SOP1` | 11 | 2×7 = 14 | 16 | 41 | 48 |
| **`SOP2`** | 11 | 3×7 = 21 | 16 | **48** | **48 精准** |
| `SOPC` | 11 | 2×7 = 14 | 16 | 41 | 48 |
| `SOPP` | 11 | imm16 = 16 | 16 | 43 | 48 |
| `SOPK` | 11 | 7 + 16 = 23 | 16 | 50 | 64 |
| **`VOP1`** | 11 | 2×8 = 16 | 21 | **48** | **48 精准** |
| `VOP2` | 11 | 3×8 = 24 | 21 | 56 | 64（8 bit 留作 `imm8` / cache 策略） |
| **`VOP3`** | 11 | 4×8 = 32 | 21 | **64** | **64 精准** |

⇒ **48-bit 只承载「全部标量算术形态 + 向量 1 源」**；**向量 2/3 源主力一律 64-bit**。
⇒ **⚠ 纠正旧结论**：「48 bit 承载典型 3 源 ALU」在真实字段下**不成立**。

### D4 —— opcode 空间分段（**统一规则**）

`op[7:6]` 为变体类，`op[5:0]` 为类内序号：

| `op[7:6]` | 段 | 项数 | 含义 |
|:---:|---|:---:|---|
| `00` / `01` | 普通 | **128** | 无谓词（仅受 `EXEC` 约束） |
| `10` | **`P` 变体** | **64** | **隐含谓词 `VP[0]`**（见 ADR-SOC-31） |
| `11` | 专用子空间 | **64** | `VOP2` = `LSU`；`SOPP` = `SYS`；其余 `fmt` 保留 |

### D5 —— 取指与对齐（四条，**必须冻结**）

| 项 | 规定 |
|---|---|
| **长度判定** | 由 `fmt` 唯一决定；**唯一例外** = `EXT` 前缀（`fmt=SOPP` 且 `op=0x7F` ⇒ 固定 64-bit） |
| **对齐** | 指令起点 **2 字节对齐** |
| **跨取指窗** | 取指窗 **16 字节**；指令**允许跨窗**，解码器持 1 条 carry-over |
| **分支目标粒度** | **2 字节** |

### D6 —— 演进机制：`EXT` 前缀（**是 TBD，不是承诺**）

`EXT` 占用 `SOPP` 的保留序号 `0x7F`，构成 64-bit 扩展形态：`ext_class 3 bit`（8 类）× `ext_op 3 bit`（每类 8 个）× **载荷 32 bit**。
⇒ **32 bit 载荷装不下矩阵类的 3 源 `AccVGPR` + dst** ⇒ **v2 的矩阵类需要 128-bit 形态** ⇒ **「v2 走 `EXT`」降级为 40 号 §8 T-10**（v2 启动前必须裁决 `fmt` 是否还留得住扩展位）。

## 3. 选项对比

| # | 选项 | 结论 | 理由 |
|---|------|:----:|------|
| **1** | **全 64-bit 定长** | ❌ 否决 | 简单，但 48-bit 形态的取指收益（标量算术）全失；且 `VOP1` 只需 48 ⇒ 浪费 16 bit/指令 |
| **2** | **全 128-bit 定长**（NVIDIA SASS 式） | ❌ 否决 | 取指带宽 ×2.67，对以标量 ALU 为主的代码不可接受 |
| **3** | **CDNA 式 32-bit 定长** | ❌ 否决 | **装不下**：控制块 16/21 bit 已占去一半，操作数无处安放 |
| **4** | **48/64 双长度变长（本 ADR）** | ✅ **采纳** | 标量算术形态恰好 48（`SOP2` 精准装满）；向量主力 64（`VOP3` 精准装满）；解码只需 2 字节前瞻；16-bit 粒度 ⇒ 对齐简单 |
| **5** | **32/48/64/128 四长度变长** | ❌ 否决 | 长度判定规则复杂度上升（`fmt` 8 类已用尽，无处放长度码）；且 32-bit 形态装不下控制块（D-2 的教训）。**过渡说明**：v2 的 128-bit 形态由 **`EXT` 前缀 + 扩展音节**承载（不经 `fmt` 长度码）⇒ 与本项否决**不冲突** |

## 4. 后果

### 4.1 正面

- **不溢出，且 3 种精准填满**：`SOP2`/`VOP1` = 48、`VOP3` = 64 **恰好**；其余 5 种（`SOP1` 41 / `SOPC` 41 / `SOPP` 43 / `SOPK` 50 / `VOP2` 56）留有 RSV 或 `imm8` 余量 ⇒ 位宽论证可机械复核；
- **解码简单**：`fmt` 在 bit[2:0] ⇒ 2 字节前瞻；16-bit 粒度 ⇒ 对齐规则单一；
- **标量与向量各自最优**：标量主力 48-bit（省取指带宽），向量主力 64-bit（够装 3 源）；
- **控制块按域裁剪的收益立刻兑现**：标量省下的 5 bit 正是让 `SOP2` 恰好装满 48 的关键。

### 4.2 负面

- **`fmt` 8/8 占满** ⇒ 未来新格式类**没有位置**，只能走 `EXT`；
- **`VOP3` 恰好 64 bit 无余位** ⇒ 任何"加一个字段"的想法（如 3-bit 谓词字段）都会把它推到 80-bit ⇒ **谓词化必须走 opcode 变体**（代价：每类只剩 128 个普通 opcode）；
- **向量 2/3 源一律 64-bit** ⇒ 向量代码的取指带宽是标量的 4/3；
- **放弃 CDNA 内联常量块** ⇒ 标量常量全走立即数 ⇒ `SOPK`（64-bit）占比可能达 30–50% ⇒ **"标量多数 48-bit"是待测假设，不是结论**；
- **`EXT` 承载力不足**（32 bit 载荷装不下矩阵类）⇒ v2 需要 128-bit 形态 ⇒ **v1 的 `fmt` 分配可能需要再扩**。

### 4.3 风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| **v2 撑破 v1 编码**（矩阵类 / 多谓词 / 标量 MCOS） | 中 | 40 号 §8 T-10 + §3.5 `EXT` 骨架；**v1 冻结前须确认 `fmt` 还留得住扩展位** |
| 标量流实际以 64-bit 为主 ⇒ 48-bit 收益落空 | 低 | B-2 后统计（V6）；结论不依赖该收益成立 |
| 变长编码增加取指器复杂度 | 低 | 16-bit 粒度 + 2 字节对齐 + 1 条 carry-over ⇒ 边界情况极少 |
| `EXT` 前缀与 `SOPP` 普通段的序号冲突 | 低 | `0x7F` 明确保留；附录 B 机械核对 |

## 6. Verification（**前瞻判据，尚未验证**）

> **判据归属**：**[本仓]** = 本仓（ArchForge，纯文档）即可关闭；**[CppTLM]** = 涉及模拟器 / 汇编器 / 差分测试 / 微基准，**在 CppTLM 仓执行**，本仓只登记关闭证据。
> 本 ADR 的划分：**本仓** = V1、V2、V7；**CppTLM** = V3、V4、V5、V6。

- [ ] **V1**〔本仓〕：**8 种形态的位宽之和逐一核对通过**（48-bit 各形态 ≤ 48；64-bit 各形态 ≤ 64） — 验证手段：40 号附录 B 检查 1/2 可执行；责任人：verifier
- [ ] **V2**〔本仓〕：**控制块字段位宽之和 = 向量 21 / 标量 16** — 验证手段：附录 B 检查 3；责任人：verifier
- [ ] **V3**〔CppTLM〕：**长度判定只依赖 `fmt`**（2 字节前瞻可判定；`EXT` 例外已单列） — 验证手段：解码器用例 —— 截断到 2 字节的指令流能正确判定长度；责任人：build
- [ ] **V4**〔CppTLM〕：**跨取指窗与跨 cache line 的指令能正确解码** — 验证手段：把一条 64-bit 指令放在 16 字节窗的边界上解码；责任人：verifier
- [ ] **V5**〔CppTLM〕：**分支目标粒度 = 2 字节** — 验证手段：全部 `SOPP` 分支目标的地址对齐检查；责任人：verifier
- [ ] **V6**〔CppTLM〕：**标量流的 48/64-bit 形态占比已统计** — 验证手段：B-2 汇编器对代表性 kernel 的统计报告；责任人：build
- [ ] **V7**〔本仓〕：**`EXT` 的承载力缺口已登记且过渡路径明确** — 验证手段：**语义判据** = 40 号 §8 T-10 不仅存在，且写明「矩阵类需 128-bit 形态」**并给出由 `EXT` 扩展音节承载的路径**（与 v1 否决四长度不冲突）；责任人：架构评审
